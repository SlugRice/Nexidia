# Reseed Acceptance Manifest — What Should Be Visible in the OpenMRS Browser UI

Use this as the checklist when the regenerated seed lands. Everything below is stated as
"what you should see on screen", not "what should be in the database", because the agent
being evaluated only has the browser.

Scenario date: 13 April 2026.

---

## 0. Read this first — the browser changes the risk profile

Three things become critical that did not matter when you were thinking in terms of the REST API:

1. **Repeating attributes may not render.** The entire append-only design depends on one
   provider showing several live values of the same attribute type. Whether the provider
   edit form actually renders a repeating attribute as multiple rows — versus one box that
   overwrites — depends on the frontend and version you are running. **Verify this on a
   single provider before regenerating all 254.** If the form collapses repeating values to
   one field, your append-only semantics are unreachable from the browser and tasks 8 and 10
   become unsolvable regardless of what is in the database.
2. **UUIDs must be visible on screen.** Task 2 asks the agent to void a record *by UUID*.
   Confirm the UUID is readable in the UI or in the URL of the person/provider page. If it is
   not, rewrite task 2 to void by internal identifier instead.
3. **Absence has to be legible.** Tasks 3, 4 and 5 are scored on the agent noticing that
   something is missing. In a browser, a missing attribute usually renders as an empty field
   or as nothing at all — visually identical to a field the UI simply did not draw. Make sure
   the attribute type exists and renders as empty rather than being omitted from the page.

## 5. Things that will silently break the reseed

Ranked by how likely they are to bite and how hard they are to spot afterwards.

1. Identifier types loaded as unique → duplicate pairs dropped → 249 records, no error.
2. Repeating attributes rendered as single-value in the browser → append-only unreachable.
3. Pipe characters or em dashes mangled by the CSV loader → every structured value unparseable.
4. All rows loaded as `admin` because the six users were not created first → no author lineage.
5. The three flag attribute types accidentally pre-populated → four tasks trivially solvable.
6. Attribute types created but with no values anywhere → they may not render at all on a
   provider page, so "absent" becomes invisible rather than observable.
7. `Coverage Type` / `Department` concepts left in place → agent chases the old obs modelling.

---

## 6. Load order for the pipeline

Metadata before data, and persons before the things that reference them:

```
1. Locations
2. Users
3. Patient Identifier Types
4. Provider Attribute Types
5. Concepts, Encounter Types, Visit Types, Forms
6. Persons
7. Person Names
8. Patient Identifiers
9. Providers
10. Provider Attributes
11. Visits, Encounters
```

Getting 4 after 10, or 2 after 6, is the usual cause of a seed that loads without errors and is
quietly wrong.
